The TRAFFIQX® Invoice API connects your application to the TRAFFIQX® network. It supports sending and receiving invoices through the customer’s chosen TRAFFIQX® provider. This plugin wraps the TIA endpoints for ZUGFeRD and structured data uploads, and for inbox and outbox operations.

Before using the API, your organization needs access to TIA and credentials for a supported provider. The provider supplies the client ID and OAuth setup; sandbox availability and configuration depend on that provider. See [TRAFFIQX® Invoice API](https://traffiqx.net/tia/) and DATEV’s [first steps](https://developer.datev.de/en/product-detail/traffiqx-invoice/1.0.0/documentation/first-steps).

For endpoint details, see the [DATEV TIA API reference](https://developer.datev.de/en/product-detail/traffiqx-invoice/1.0.0/reference/reference-overview/traffiqxinvoice).

        ```ts title="invoicer.ts"
                            clientId: process.env.B4VALUE_CLIENT_ID!, // [!code highlight]

                        }), // [!code highlight]

                            clientId: process.env.BUNDESDRUCKEREI_CLIENT_ID!, // [!code highlight]
                        }), // [!code highlight]
                    ], // [!code highlight]
                }), // [!code highlight]
            ],
            // ...

        ```

## Provider

The plugin accepts one provider or an array of providers. With an array, pass `providerId` to every operation so the plugin can route the request to the matching base URL and provider-specific headers. The value must match the selected factory's `providerId` exactly (for example, `b4value.net GmbH`). With one configured provider, `providerId` is optional. Use the client ID and sandbox setting issued for each provider.

## Usage

Every operation accepts `providerId`. It is required when `provider` is configured as an array and optional when a single provider is configured. Use the exact provider ID shown by the selected provider factory.

### Upload ZUGFeRD Invoices

Customers can upload a document data in the ZUGFeRD format to the outbox workspace so that an invoice can be created from them.

```ts
const pdf = await invoicer.toPDF(await readFile("./invoice.pdf"));

const { data, error } = await invoicer.traffiqx.upload({
    data: await pdf.save(),
    traffiqxId: "0042000711688",
    providerId: "b4value.net GmbH",
    accessToken: async (ctx) => {
        // Return provider access token
        return await getAccessToken(ctx.meta.userId);
    },
    // Additional metadata accessible in context
    meta: {
        userId: "12345",
    },
});
```

        ### Retrieve an accessToken

        The following example will use the `b4value` provider.

        ```ts
        async function getAccessToken() {
            const accounts = await auth.api.listUserAccounts({
                headers: await headers(),
            });

            const account = accounts.find((acc) => acc.providerId === "b4value");

            if (!account) {
                throw new Error("B4Value account is not linked");
            }

            const { accessToken } = await auth.api.getAccessToken({
                body: {
                    accountId: account.id,
                },
                headers: await headers(),
            });

            return accessToken;
        }
        ```

        For more details, please refer to the [official Better Auth Documentation](https://better-auth.com/docs/concepts/oauth#get-access-token).

## Best Practices

- Run uploads and follow-up status checks in a durable background worker. Persist the job state so transient failures or process restarts do not lose track of a document.
- Make uploads idempotent in your application. Create a stable idempotency key for each business document, record the returned `document_id`, and check that record before retrying a request whose outcome is unknown. The TRAFFIQX plugin does not provide an idempotency key itself.
- Retry transient failures with bounded exponential backoff. Before retrying an upload after a timeout, reconcile against the outbox so a successful request with a lost response does not create a duplicate.
